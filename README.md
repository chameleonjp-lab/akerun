# Vault Tumbler Lab / akerun

金庫の内部機構を観察し、反応を比べ、仮説を修正して開錠するブラウザゲームです。単純な数字合わせではなく、ダイヤル、ホイール、フライ、偽ゲート、テンション、フェンス、ロックボルト、扉側ボルトを一つの流れとして扱います。

## 現在のプレイ

1. タイトルでプレイヤー名を入力する
2. 進行ゲームでは、未クリアの初級問題から順番に一問が選ばれる
3. 自由練習では、公式20問から問題と難度を選べる
4. 本日の競技では、日本時間の日付に対応する同じ問題へ全員が挑戦する
5. 接触反応を観察し、ホイールを順に整列する
6. テンション、フェンス、ロックボルト、扉ハンドルを操作する
7. 結果画面で時間、失敗、回転量、偽ゲート接触、スコアを確認する

後半の作業台では、針が現在の入力位置、針の下の細い表示が保持進行です。保持判定へ入ると作業台の見出しが「帯域内 / 保持」に変わり、位置が外れると「要調整」に戻ります。OBSERVEではテンションとフェンスの安定帯も重ねて表示し、ロックボルトと扉ハンドルには成功閾値の目印を表示します。標準以上では帯域そのものを隠したまま、抵抗の変化とこの状態表示を手掛かりにします。

初回は、ダイヤル、接触判別、後半機構、短い完全開錠の4段階訓練を用意しています。

ダイヤルの正規ゲートは、回転入力の途中で通過しただけでは確定しません。正規ゲートに触れた位置で回転を止めたときだけ、指定された通過回数へ進みます。偽ゲートは接触した瞬間だけでなく、その一刻み手前・後ろの縁も別の反応として返るため、候補を止めて比較できます。

訓練後の `AKERUN-01-V1` と `AKERUN-02-V1` は導入ガイドとして、正規ゲート・偽ゲートの位置と具体的な通過指示を表示します。問題の目標、状態機械、採点、操作履歴は標準問題と同じです。`AKERUN-03-V1` から内部の正解位置を遮蔽した通常の観察へ移ります。

## 公式20問

通常プレイは OFFICIAL_PROBLEM_CATALOG を使います。問題には次の値を固定しています。

- 問題IDと問題バージョン
- 金庫型、ホイール数、目標位置、開始方向
- 通過回数、偽ゲート位置・深度、金庫固有の予圧
- 基準時間、基準回転数、基準失敗数、基準偽ゲート接触数、難度補正

自動seed生成は開発・検査用として残し、通常プレイへ直接出さない構造にしています。

## 三種類の金庫の個性

同じ手順を数字だけで繰り返さないよう、金庫ごとに観察の重点を変えています。

- Aurora：正規ゲート、ゲート縁、偽ゲートの接触差が大きく、反応を読みやすい
- Nocturne：偽ゲートが多く、正規ゲートに近い音と反応を返すため、候補を比べて判断する
- Pelagic：回転速度で接触の深さが変わり、全ホイールを揃えた後に停止後の反応を待つ

偽ゲートの縁は正規ゲートの縁とは別の接触プロフィールです。正解確定ではないため、縁で止まらず、深さ・抵抗・フライ接続を合わせて判断します。

Pelagicの停止待ちは一時停止ではありません。プレイ時間は進みますが、急いでテンションを掛けても先へ進めないため、止めた後の観察そのものが判断になります。

## 収蔵品

収蔵品は30種類あり、通常品18、希少品9、特別品3に分かれます。単純な低確率抽選ではなく、開錠結果に応じて解放します。

- 特定問題のクリア
- 失敗0、または指定回数以内
- 基準回転数以内
- 観察精度やスコアの条件

訓練、お手本、開発用seed、リタイアでは解放しません。収蔵品は能力を強化せず、鑑定帳の記録と再挑戦の目標として使います。

## 音の試験室

設定またはタイトル画面から、空転、ゲート縁、偽ゲート、フライ接続、深い接触、フェンス、ボルトの音を聞き比べられます。各音には、画面で確認できる反応も短く表示します。

音をOFFにしても、画面の変化、抵抗、短い文章で同じ情報を返します。振動は音とは別にON/OFFでき、振動に対応しない端末でも開錠できます。

## スコア

時間だけでなく、次を使ってスコアを計算します。

- 経過時間
- 総ダイヤル移動量と基準との差
- 問題ごとの基準失敗数との差
- 基準通過を除いた余分な偽ゲート接触数
- 問題の難度補正

結果画面の偽ゲート接触数は物理的な通過総数を表示します。正しい最短経路でも通過する問題固有の基準数は二重に減点せず、基準を超えた分だけスコアと観察精度へ反映します。

高コントラスト、低モーション、精密入力、音・振動の切替はスコアを下げません。

後半で過負荷が起きた場合は、作業台の「力を抜いて解除」をタップして離します。テンションの過負荷はテンション確認へ、フェンスの過負荷は直前の整列を少し戻した状態へ復帰します。失敗数が上限に達した場合はRESETで最初からやり直します。

採点契約は `V3` です。既存の `parTime` は機械監査で得た基準値なので、そのまま人間の時計に使わず、暫定的に10倍した観察時間基準へ展開します。時間ボーナス／ペナルティ、回転差、失敗差、余分な偽ゲート減点には上限を設け、通常の観察プレイが0点へ落ちにくくしています。60秒以内の速度ボーナスを別枠で設け、短時間の速度プレイだけが10000点を越えられるようにしています。実機計測後に時間基準を更新する場合は、採点契約版も更新します。

## 保存とランキング

プレイヤー名、訓練完了、問題別自己ベスト、送信失敗結果、収蔵品の解放状態を端末内へ保存します。

ランキングは、カメレオンJPの実験場で使っている共通の `games`、`game_scores`、`score_runs` を参照します。Akerun専用の公開ランキングテーブルは作りません。書き込みだけは、既存の verified ゲームと同じく Edge Function を入口にします。

- game slug: akerun
- 送信: `supabase/functions/akerun-competition` の prepare / begin / abandon / finish
- 取得: `get_akerun_ranking_v2`（V3採点契約。旧V1/V2の記録は現行ランキングから除外）
- サーバーが発行するプレイIDで、問題ID・問題バージョンをプレイ中に固定する
- 初回抽選と別問題はサーバー抽選。同じ問題の再挑戦だけ、完了済みの同一問題トークンを提示する
- サーバー側の公式問題カタログで余分な回転、観察精度、スコアを再計算する
- `finish` には、回転方向とテンション・フェンス・ボルト・ハンドル操作を時刻順に並べた `operationTrace` を含める
- Edge Functionは同じ決定的な機構ルールを操作履歴から再生し、開錠状態と回転数・失敗数・偽ゲート数・余分な回転・観察精度・スコアが送信値と一致しない結果を拒否する
- 履歴が上限を超えて途中で切れた場合は、証拠を欠くためランキングへ送信しない
- 問題ごとの最低必要回転数を下回る `finish` はサーバーで拒否する
- `begin` から `finish` までのサーバー経過時間を記録し、1秒未満またはサーバー計測値より3秒を超えて短い報告時間を拒否する
- 基準偽ゲート接触を除いた余分な接触数を、観察精度とスコアの検証値として送る
- 順位はスコア降順、失敗数、時間、余分な回転数の順で比較する
- 公開クライアントではPublishable keyだけを使用
- 訓練、お手本、リタイア、未クリアは送信しない
- 通信失敗時はプレイIDを含む結果を端末内へ保存し、結果画面またはタイトル画面から再送する
- `prepare`だけ完了して`begin`の確認に失敗した実行は、クライアントが`abandon`を送り、サーバー側でも競技用トークンを破棄する。リタイアや公式リセットも同じ処理を通り、通信断時は破棄待ち情報を端末へ保存して次回起動・次回開始時に再送する。破棄確認まで届かない場合、開始前の予約は短い期限で失効し、開始済みの実行は24時間の再送保持を続ける
- プレイ中は機構状態と計測値を端末チェックポイントへ保存し、再読込時も計測を初期化せず復元する。再開時は問題固有のstage、固定ホイール、プロトコルphase、後半アクチュエータの整合性も検証し、旧形式や壊れた保存データでは検証済みプレイIDを再利用しない
- 開錠を検知した時点で結果を端末内へ先に保存し、進行中のプレイ記録を削除する。結果画面へ移る前にSafariが終了しても、同じプレイを途中から再利用せず、保存済みの結果を再送できる

Supabase側の `akerun` は `submission_mode=verified` で登録しています。2026-08-29の読み取り確認では、公式問題20件、実行記録0件、ランキング記録0件で、`is_active=false` と `accepting_runs=false` を維持していました。V3採点契約migrationも受付を無効のまま更新し、旧集計を現行ランキングから隔離します。migration適用後に、Edge Functionと設定の版、公式問題件数、実行記録0件、ランキング記録0件、停止状態を再確認してから受付を判断します。通常プレイ自体は端末内記録として続けられます。サービスキーはEdge Functionのサーバー環境変数だけで使用し、ブラウザへ出しません。

この契約は、問題の固定、スコア再計算、値の範囲、操作履歴の決定的な再生、二重送信を検証します。ただし、操作履歴が実際の人間の指や端末から発生したことまでは証明しません。接続元・名前・端末単位の制限と、実機での公平性確認は後続段階です。

## iPhone操作

native Canvas 2D上でダイヤルと物理部品を指で操作できます。論理座標と画面密度を分離し、端末のDPRは最大2までに制限します。画面外へ移動した場合やバックグラウンドへ移った場合は入力を安全に解除し、ゲームを自動一時停止します。非表示中はrequestAnimationFrameを停止し、復帰時に再開します。BLINDではダイヤル中は横ドラッグ、全ホイール整列後は現在の部品へ同じドラッグを渡します。フェンスは上方向、それ以外の後半部品は右方向へ動かします。

React側にはタイトル、名前入力、訓練、HUD、一時停止、結果、ランキング、収蔵品、設定、ヘルプを配置しています。キーボード操作は補助であり、ゲーム開始や開錠に必須ではありません。

## 公開

mainへのマージで `.github/workflows/deploy-pages.yml` が静的サイトをビルドし、公開前に未設定の解析値、旧環境の外部パス、参照切れ素材を検査してからGitHub Pagesへ配置します。公開URLはリポジトリの `/akerun/` 配下を前提にし、Viteの `VITE_BASE_PATH` で同じ成果物をローカルとPagesへ出力します。

タイトル画面には `BUILD / <12文字>` を表示します。公開画面の `data-build-commit` とGitHub Actionsのコミット番号を照合して、表示中の画面がmainのどのコミットから生成されたか確認できます。公開後のHTML、JavaScript、CSS、faviconは同じワークフロー内でHTTP 200を確認します。

- client/src/game/RunLifecycle.ts: 公式プレイのリセット・実行ライフサイクル規則
- client/src/game/ProgressStore.ts: 端末内進行保存と再送待ち

- client/src/game/ObservationLedger.ts: 観察メモの端末内保存

- client/src/game/OfficialProblemBalance.test.ts: 20問の開錠可能性・重複・極端値・表同期テスト

## 開発コマンド

```bash
pnpm check
pnpm test:rules
pnpm generate:problem-balance
pnpm build
pnpm build:pages
pnpm verify:static-build
```

`pnpm generate:problem-balance` は、公式20問を既存の機構で自動解法し、基準値と自動監査結果を `docs/official-problem-balance.md` へ出力します。問題定義や機構を変更したときは、表を再生成してからテストします。

GitHub Actionsでも型検査、ルールテスト、本番ビルド、GitHub Pages用静的ビルドを実行します。
